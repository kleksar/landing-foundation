# Landing Foundation

Основа для разработки индивидуальных лендингов и небольших статических сайтов с помощью ИИ.
Один сайт на репозиторий; Bun / React / Vite / TypeScript. Композиция, тексты, типографика,
палитра и анимации выбираются под задачу клиента.

**Статус: самостоятельный starter; основной CI прошёл 59 тестов. Для этапа 4.2
подготовлен отдельный CI совместимости, его первый запуск ещё не подтверждён.
Это ещё не выпущенный GitHub template.**
Результаты приёмки и ближайшая задача записаны в [дорожной карте](docs/roadmap.md).
[Проба реализации](docs/evaluations/implementation.md) описывает отдельный пример и найденный
при визуальном осмотре дефект; его оформление не переносится в общий starter.
[AGENTS.md](AGENTS.md) задаёт правила работы агента.

Для нового сайта или продолжения в другом чате передайте актуальную копию проекта и
попросите прочитать `AGENTS.md`. Агент разберёт задачу и сохранит решения в `PROJECT.md`.
Примеры входного запроса и границы доступа: [workflow](docs/workflow.md).

## Получение проекта

```bash
git clone git@github.com:kleksar/landing-foundation.git
cd landing-foundation
```

Если переносите основу из архивной контрольной точки, загружайте на GitHub содержимое
внутренней папки проекта: `package.json`, `AGENTS.md` и `.github/workflows/ci.yml` должны
находиться непосредственно в корне репозитория. Внешняя папка архива и диагностические
логи не входят в starter.

## Запуск

Используем Bun 1.4.0 и Node 24.20.0. Bun устанавливает зависимости и запускает задачи;
CLI React Router использует Node. Устанавливаем зависимости из корня репозитория:

```bash
bun install --frozen-lockfile
bun run dev
```

Для production-сборки и её локального просмотра:

```bash
bun run build
bun run preview
```

Статический результат находится в `build/client`. Node и Bun на хостинге не требуются.
`preview` — локальный сервер для проверки сборки. Инструкции по размещению, HTTPS,
обновлению и откату будут реализованы и проверены на этапе 5.

## Где работать

| Что меняем | Где |
| --- | --- |
| Страницы, компоненты, стили | `app/` |
| Статические ресурсы | `public/` |
| Требования и тексты | `SITE_SPEC.md` |
| Решения, открытые вопросы и следующий шаг | `PROJECT.md` |
| Визуальное направление | `DESIGN.md` |
| Метаданные и canonical URL | `site.config.json` |
| Список prerender-маршрутов | `rendering.config.json` |
| Валидация конфигурации и crawler-файлы | `lib/site-contract/` |
| Проверки размера сборки и локальный сервер | `tooling/` |

Один `package.json`, один `bun.lock`, один сайт. Генератор `create:landing` удалён;
новые сайты начинаются с отдельной копии основы. Входной workflow проверен на учебных
брифах. Навык содержания готовит структуру и тексты в `SITE_SPEC.md`, дизайн-навык —
визуальные правила в `DESIGN.md`. `landing-tooling` подбирает средства реализации по этим
требованиям и сохраняет обоснование. Текущие примеры страницы не задают обязательный дизайн.

### UX/UI-навыки

`landing-design` и `visual-qa` используют выборочную адаптацию
[ux-ui-agent-skills](https://github.com/plugin87/ux-ui-agent-skills/tree/2ffb677aa02b225c8a3da1b7f31d9ebb7c38f1dd):
композиция под бриф, различимые варианты и ревью с наблюдаемыми доказательствами.
[Локальная инструкция и источники](.agents/skills/landing-design/references/ux-ui-agent-skills.md)
закреплены на конкретном коммите. Это дополнение к существующим навыкам, не установка всего
пакета: нет новых slash-команд, зависимостей, обязательной темы или автозапуска upstream-скриптов.
Дополнительная установка не нужна; агенту достаточно прочитать `AGENTS.md` и применимый навык.
Автозагрузка в конкретном агентном клиенте и улучшение визуального качества ещё требуют проверки.

## Проверки

Один раз устанавливаем браузер для Playwright:

```bash
bunx --no-install playwright install chromium --no-shell
```

На чистой Debian/Ubuntu-машине вариант
`bunx --no-install playwright install --with-deps chromium --no-shell` также устанавливает системные
библиотеки. CI использует этот вариант.

```bash
bun run audit
bun run test:unit
bun run test:repo
bun run test:e2e
bun run verify
```

`test:e2e` сначала создаёт новую сборку. `verify` объединяет lint, typecheck, unit,
repository contracts, build, build contracts и E2E; `audit` запускается отдельно.
Основной E2E использует полный Chromium в modern headless. Перед выпуском сайта и после
изменений, чувствительных к браузеру, запускаем `bun run test:compat`: те же проверки в
Chrome Stable, Firefox и WebKit с обычным motion-режимом. На GitHub это можно выполнить через
**Actions → compatibility → Run workflow**: браузеры устанавливает runner. Этот workflow
также запускается при push в `main` изменений тестов E2E, Playwright-конфига, manifest,
lockfile или самого workflow. Для правок приложения/CSS нужен ручной запуск перед выпуском.
Локальная установка браузеров и ограничения — в стратегии тестирования ниже.

Подробности: [архитектура](docs/architecture.md), [стратегия тестирования](docs/testing.md).
[Baseline этапа 2.1](docs/baseline.md) описывает проверки прежнего прототипа;
результаты текущей миграции находятся в дорожной карте.
